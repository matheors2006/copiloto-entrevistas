# SPEC.md — Interview Copilot System Specification

Spec Driven Development (SDD) reference for the Interview Copilot. This document is the
source of truth for the system's architecture, data flow, WebSocket protocol, and
concurrency model. Any behavioral change to the pipeline described here should update this
file in the same commit.

## 1. System overview

Interview Copilot is a desktop overlay that listens to system audio during a live interview
call, transcribes the interviewer's question in real time, and streams back short
first-person "talking points" the candidate can say out loud — grounded in the candidate's
own CV.

```
┌─────────────────────┐        WebSocket /ws        ┌──────────────────────────┐
│   Tauri overlay UI   │◄────────────────────────────►│   FastAPI backend        │
│   (React, App.tsx)   │        HTTP /upload-cv       │   (main.py)              │
└─────────────────────┘◄────────────────────────────►└──────────────────────────┘
                                                              │            │
                                                     audio    │            │ question text
                                                  (loopback)  ▼            ▼
                                                   ┌────────────┐   ┌─────────────┐
                                                   │  Deepgram  │   │    Groq     │
                                                   │  streaming │   │  (LLM API)  │
                                                   │  STT API   │   │             │
                                                   └────────────┘   └─────────────┘
```

## 2. Components

| Component | File(s) | Responsibility |
|---|---|---|
| Desktop overlay | `desktop-ui/src/App.tsx` | Always-on-top floating window; renders the live question, translation, and talking points; drives pause/force-response controls; uploads a new CV PDF. |
| WebSocket server | `backend/main.py` | Orchestrates the pipeline: captures loopback audio, forwards it to Deepgram, reacts to transcription events, invokes the LLM engine, and pushes results back to the UI. |
| CV upload endpoint | `backend/main.py` (`POST /upload-cv`) | Accepts a PDF, extracts its text, and hands it to the LLM engine to regenerate the structured CV profile. |
| LLM reasoning engine | `backend/llm_engine.py` | Builds the system/user prompts, calls Groq for streamed talking points and for English→Spanish translation, and re-derives the structured CV JSON from raw PDF text. |
| Candidate profile | `backend/cv_mock.json` | Structured JSON profile (skills, projects, competencies) that grounds every LLM answer. Regenerated by `/upload-cv`. |

## 3. Data flow

### 3.1 Happy path (spoken question → answer)

1. `pump_loopback_audio` continuously records the system's default output device via WASAPI
   loopback (`soundcard`) in `BLOCK_SIZE`-sample chunks, converts them to 16-bit PCM, and
   streams them to the open Deepgram connection (`send_media`).
2. Deepgram emits streaming `Results` events. Each event's transcript fragment is appended to
   `accumulated_transcript` and echoed to the UI as an `interim_question` event so the
   candidate sees the question building up live.
3. When Deepgram marks an utterance as `speech_final` (end of a spoken turn, based on
   `endpointing`), the backend:
   - Joins and clears `accumulated_transcript` into `full_question`.
   - Cancels any in-flight `llm_task` / `translation_task` from a previous question.
   - Detects the question's language from Deepgram's `alternatives[0].languages` (with a
     keyword-based fallback, `looks_like_english`, when that metadata is absent).
   - Emits `question` (the final transcript) and `clear_answer` (resets the UI's answer pane).
   - Launches `run_llm_response` as an independent `asyncio.Task`, which streams
     `answer_token` events from Groq.
   - If the question was detected as English, also launches `run_translation` as an
     independent task, which emits a `translation` event once Groq returns the Spanish
     translation.
4. The UI accumulates `answer_token` events into the visible talking points and renders the
   `translation`, if any, under the question.

### 3.2 Manual override (Force Response)

The candidate can click "⚡ Forzar Respuesta" at any time. This sends `{"type":
"force_response"}` over the WebSocket. The backend's `listen_to_client` loop treats this the
same as a `speech_final` event, except the question text comes from whatever is currently in
`accumulated_transcript`, falling back to `last_question` (the most recent finalized
question) if the transcript buffer is empty. This exists for cases where Deepgram's
endpointing is slow to fire, or the candidate wants to re-run the LLM on the last question.

### 3.3 Pause / Play (context muting)

The candidate can click "⏸ Pause" to stop the assistant from listening during small talk,
without tearing down the Deepgram connection (which would cost reconnect latency on the next
real question). This sends `{"type": "toggle_pause", "state": true|false}`.

- On the backend, `listen_to_client` flips a connection-scoped `PauseState.is_paused` flag.
- `pump_loopback_audio` checks this flag on every loop iteration. While paused, it **does not**
  record or send real audio; instead, it periodically calls `connection.send_keep_alive()`
  (a Deepgram `KeepAlive` control frame, not billed as transcribed audio) every
  `KEEP_ALIVE_INTERVAL_SECONDS` seconds, which prevents Deepgram's inactivity timeout from
  closing the socket.
- On resume, the loop immediately falls back to recording and streaming real audio — no
  reconnect is needed, so the very next spoken question is captured with no cold-start delay.

### 3.4 CV upload

`POST /upload-cv` receives a PDF, extracts raw text via `pypdf`, and calls
`procesar_cv_pdf`, which asks Groq (with `response_format={"type": "json_object"}`) to
convert the raw text into the app's structured CV schema, then overwrites `cv_mock.json`.
Every subsequent LLM answer, in every WebSocket connection opened after the upload, is
grounded in the new profile. Errors are surfaced as `HTTPException` (400 for an
unreadable/empty PDF, 500 for any other processing failure) with CORS headers intact.

## 4. WebSocket event dictionary (`/ws`)

### Server → Client

| Event `type` | Payload | When it's sent |
|---|---|---|
| `interim_question` | `{ text: string }` | On every non-final Deepgram transcript fragment, so the question streams in live before it's finalized. |
| `question` | `{ text: string }` | When a question is finalized — either by Deepgram's `speech_final`, or by a manual `force_response`. |
| `clear_answer` | `{}` | Immediately after `question`, telling the UI to reset the talking-points pane before new tokens arrive. |
| `answer_token` | `{ text: string }` | One per streamed token from Groq's chat completion; the UI appends these to build the answer incrementally. |
| `translation` | `{ text: string }` | Once, when the finalized question was detected as English and Groq's fast translation model returns a Spanish translation. |

### Client → Server

| Event `type` | Payload | Effect |
|---|---|---|
| `force_response` | `{}` | Manually finalizes the currently accumulated (or last known) question and re-runs the LLM/translation pipeline on it. |
| `toggle_pause` | `{ state: boolean }` | Mutes (`true`) or resumes (`false`) audio capture without closing the Deepgram connection. |

## 5. Concurrency model

Each `/ws` connection runs three long-lived `asyncio.Task`s concurrently, plus short-lived
per-question tasks:

- **`listen_task`** — `connection.start_listening()`. Reads Deepgram's event stream and
  invokes `handle_deepgram_message` for each message. Deepgram's SDK (`_emit_async`) awaits
  each callback before reading the next message, so this callback must never block on slow
  I/O.
- **`audio_task`** — `pump_loopback_audio`. Captures and streams microphone/loopback audio (or
  keepalives while paused). Runs independently of the LLM pipeline.
- **`client_listener_task`** — `listen_to_client`. Loops on `websocket.receive_text()` for the
  lifetime of the connection, handling `force_response` and `toggle_pause`. Ends only when the
  client disconnects (raising `WebSocketDisconnect`).
- **`llm_task`** (per question) — `run_llm_response`, created via `asyncio.create_task(...)`
  from inside `handle_deepgram_message` or `listen_to_client`. **Never awaited directly** from
  those callbacks — doing so would block the Deepgram listen loop (`listen_task`) for the
  entire duration of the LLM stream, causing the well-known "freeze after 2-3 questions" bug.
  Cancelled and replaced whenever a new question is finalized before the previous answer
  finishes.
- **`translation_task`** (per question, English only) — `run_translation`, same
  fire-and-forget pattern as `llm_task`.

All WebSocket sends (from the main handler and from every background task) go through
`send_json_safe`, which serializes them behind a single `asyncio.Lock`. Without this lock,
concurrent `websocket.send_json()` calls from different tasks can interleave and corrupt the
WebSocket frame stream — this was a real, previously-unreported bug found while stabilizing
the pipeline.

The connection's outer `async with ... connect(...) as connection:` block waits on
`asyncio.wait({listen_task, audio_task, client_listener_task}, return_when=FIRST_COMPLETED)`.
Whichever task finishes first (normally `client_listener_task`, on disconnect) triggers
cleanup: every remaining task, plus any in-flight `llm_task`/`translation_task`, is cancelled
and awaited with `return_exceptions=True`.

## 6. Prompt engineering: dynamic language lock

`stream_respuesta(pregunta, cv_json, idioma_detectado)` sends three messages to Groq: the
persona/style system prompt, the user message (question + CV JSON), and a **final** system
message built by `build_language_lock_prompt(idioma_detectado)`. Putting the language lock
last (after the CV, which is often in Spanish) exploits recency bias so the detected language
of the *current spoken question* — not the CV's language — determines the response language.
This was tightened after empirically observing that Spanish-language tone examples in the
persona prompt could otherwise leak into English-language answers.

## 7. Error handling contract

- `stream_respuesta` and `traducir_pregunta` catch all Groq exceptions internally, log them,
  and end gracefully (empty generator / `None` return) instead of propagating — a Groq
  timeout or rate limit must never take down the WebSocket connection.
- `send_json_safe` catches all WebSocket send exceptions and logs them instead of raising.
- `/upload-cv` catches PDF-parsing and LLM extraction errors and re-raises them as
  `HTTPException` (400 for empty extracted text, 500 for anything else), so CORS headers are
  still attached to the error response.
